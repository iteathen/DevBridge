# Windows audit handoff

The admitted Windows 11 Pro installation at recipe v3 passed the product-key page, expanded its system disk to 17,754,488,832 bytes, and booted the installed operating system. The native console at 15:24:34 UTC showed Administrator automatic sign-in rejected with an incorrect-password message. The previous recipe supplied the account password in oobeSystem but omitted auditSystem automatic logon. Preserve that subject and its evidence.

Microsoft's [built-in Administrator guidance](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/enable-and-disable-the-built-in-administrator-account?view=windows-11) requires both AutoLogon and UserAccounts/AdministratorPassword in auditSystem. Recipe v4 supplies both from the same temporary construction credential. The credential remains outside public recipe evidence and is not a host account or activation key.

Microsoft documents an [extra-logon count behavior](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-shell-setup-autologon-logoncount). The initial audit handoff therefore disables automatic logon, sets its remaining count to zero, and removes the stored automatic-logon password before the idempotent readiness check. Final image sanitation also removes the count with the existing credential cleanup.

Scope is the unattended recipe and its cleanup; provider and lifecycle authority stay unchanged. Verify the parsed auditSystem settings use the exact same escaped password, preserve source index selection, keep the ready guard idempotent, and exclude credentials from public evidence. Native acceptance requires a fresh subject reaching the powered-off audit handoff and subsequent normal production qualification. Configuration tests alone do not prove that frontier.

## Native audit and command boundary

Recipe v4 authenticated Administrator and entered auditUser. Native setup logs then rejected its 292-character RunSynchronous/Path with error 0x80220005. Microsoft limits that setting to [259 characters](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-deployment-runsynchronous-runsynchronouscommand-path) and directs synchronous commands not to shut down Windows themselves.

Recipe v5 stages the audit helper on the installed system during specialize using a bounded command. The oobeSystem [Reseal/Audit/ForceShutdownNow setting](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-deployment-reseal) owns the installation shutdown. After the existing construction owner detaches media and starts the installed disk, auditSystem signs in and auditUser runs the short local helper. That helper clears automatic logon and records readiness without scheduling another shutdown. Finalization removes the staged helper. Validate the decoded command lengths and that auditUser needs no attached setup media.

Native PowerShell Direct diagnostics also exposed host module autoload failure for ConvertTo-SecureString. Both Hyper-V guest-command and bridge adapters now construct, make read-only, and dispose the credential's .NET SecureString directly. The same ordinary-token guest-command adapter then authenticated the exact v4 VM and returned OS/readiness information. No host module installation, elevated guest-command bypass, or new transport was needed. The bridge adapter has matching focused regression coverage; its end-to-end run remains pending.

## Guest service startup

Review of the next provisioning stage found that the seed agents were registered directly as Node executables. Windows services require an [SCM entry point](https://learn.microsoft.com/en-us/dotnet/api/system.serviceprocess.servicebase.run?view=netframework-4.8.1). The guest-only service adapter supplies ServiceBase startup/stop/shutdown for the two fixed seed identities, keeps each worker tree in a job, and reports unexpected worker exit as service failure. It accepts no caller-selected path or command. Provisioning compiles locally bound source with the built-in framework compiler, registers the resulting service executable, and qualification checks the exact service command after reboot.

The service correction occurs before this subject's first provisioning attempt and leaves its admitted OS media, unattended recipe, tool versions, and guest scripts unchanged. It requires no repeat of the completed OS installation. Native compiler validation and rejection of unknown/extra service arguments passed; SCM startup and post-reboot service readiness still require the production qualification run.

The first transition into `prepare-attempted` exposed an invocation policy mismatch before a child could start: preparation requested 60 minutes through a default invoker capped at five minutes. Production guest operations now use the existing configurable 45-minute ceiling, and preparation requests that same bounded duration. Management operations keep their original invoker, injected adapters remain under their caller's policy, and the saved installation deadline is unchanged.

The native guest then installed the pinned Visual Studio Build Tools 17.14.37614.0, Node 22.23.2, and Git 2.55.0.windows.5 successfully. Preparation stopped while importing VsDevCmd's environment: nested outer quotes made `cmd` treat the beginning of the Program Files path as an invalid command. The corrected batch invocation quotes its path using `call` and rejects nonzero initialization before recording machine environment values. This follows Microsoft's [cmd quoting rules](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmd). A native regression executes the generated import statement against a batch fixture under directories containing spaces and proves both environment capture and failed-initialization rejection. Reconciliation retains the completed installation and exact tools.

## Native qualification and finalization lifetime

V5 subsequently passed native CMake/CTest, network, exact toolchain, and service qualification after reboot at 16:18:15 UTC. MSVC was 19.44.35228.0 and CMake was 3.31.6-msvc6. The finalizer then disabled its construction account and returned immediately after launching Sysprep. The guest remained running and idle, and the disabled credential could no longer read diagnostic logs. Microsoft documents that [Start-Process children in remote sessions terminate when the session ends](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-7.5). The adapter closes that session on return, so its asynchronous finalizer did not provide the required process lifetime.

The host's waiting continuation was cancelled before preserving the VM in Hyper-V Saved state at 16:28:26 UTC. Saved state is deliberately not an apparent successful shutdown. The disk, memory, qualification, and incomplete finalization records remain available; this subject must not be resumed as a completed image or forcibly powered off and then treated as Sysprep success.

Generation v6 runs Sysprep with `/quit` and `-Wait` in the remote session, checks its exit status, then disables construction access and schedules shutdown. The operation receives the existing 30-minute finalization allowance. This uses Microsoft's supported [Sysprep command-line options](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/sysprep-command-line-options?view=windows-11). Native fixture tests prove successful completion and rejection of a failed process before account cleanup. The generation changes so the abandoned v5 finalization cannot supply v6 image evidence. Native v6 image qualification is pending.
