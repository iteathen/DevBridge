## Research conclusion at this checkpoint

The initial Windows options considered were:

- Windows Sandbox VM: strong isolation but too heavy/awkward for ordinary per-operation build/test workflow.
- Job Objects alone: rejected because they provide process-tree management, not the required filesystem/credential/Git/network isolation.
- direct custom AppContainer/Base Process Container integration: viable but would require substantial custom native launcher/policy work.
- Microsoft eXecution Container (MXC) `processcontainer`: selected as the current integration direction because it is designed for sandboxed execution of untrusted/model/tool code, exposes a Windows ProcessContainer backend, supports policy-driven filesystem/network/UI restrictions, ships a Node-compatible/native launcher path, and maps well onto DevBridge's existing sandbox-provider port.

The implementation pins `@microsoft/mxc-sdk` version `0.7.0` and uses its `wxc-exec.exe` runtime rather than adding the SDK as a normal application dependency.

### Critical upstream caveat

MXC is still Public Preview / early preview. Its upstream README explicitly warns that policies may be overly permissive and that MXC profiles should not currently be treated as security boundaries on their own.

Therefore this branch deliberately does **not** trust MXC package presence, schema declarations, or `--probe` alone. DevBridge's own adversarial live boundary probe remains the gate for `verified: true` and `repositoryCodeExecution: true`.

This caveat must be reassessed before merge. If the live probe cannot prove every DevBridge invariant on the intended Windows host/CI image, the provider must stay fail-closed or the backend choice must change.

### Worker IPC adaptation

The existing worker-exchange contract used Bubblewrap-only guest paths under `/run/devbridge-exchange`.

Windows ProcessContainer does not provide that bind-mount alias primitive, so this branch adapts the worker-exchange contract:

- Linux/Bubblewrap retains fixed guest mount targets;
- Windows uses host-side staging paths under the control-owned worker-exchange area;
- the context remains control-owned/read-only;
- worker output is written to a non-authoritative staging result file;
- DevBridge imports/copies staged bytes back into the anchored authoritative result file before privileged consumption;
- authoritative result/context identity validation remains in DevBridge;
- the Windows worker is not supposed to receive broad read/write access to the state directory.

This area is security-critical and needs adversarial Windows validation.

### Process-runner cleanup

Both model-worker and deterministic process runners were adjusted so a provider may return a cleanup callback for provider-owned scratch/staging lifecycle.

The intent is that the Windows adapter can allocate disposable sandbox scratch without leaking it, while retaining the same process-runner authority model.

## Important unresolved technical risks

### 1. MXC preview security status

This is the largest architectural risk. Do not merge because MXC is convenient. The DevBridge acceptance probe must be treated as mandatory evidence, and the intended deployment host needs real qualification.

### 2. Windows `deniedPaths` / nested policy behavior

The current provider puts the project root in `readwritePaths` and `.git` in `deniedPaths`.

MXC documentation contains warnings/limitations around Windows denied-path support. The live `.git` mutation probe should fail verification if nested denial is not actually enforced, which is the correct fail-closed outcome, but this may mean the current policy does not become usable on the target host.

Before changing policy, research the exact Windows `processcontainer` path-precedence/enforcement behavior for the pinned MXC version and target Windows build. Do not silently weaken `.git` isolation to gain functionality.

Potential alternatives if needed include a separately projected working tree without writable Git admin state, a read-only `.git` policy if most-restrictive nested paths are demonstrably enforced, or a different Windows containment backend.

### 3. MXC DACL fallback

The current config allows `fallback.allowDaclMutation: true`.

MXC documents this as a fallback that temporarily modifies host filesystem security descriptors and restores them on exit. This may be necessary for Windows 11 24H2 compatibility, but DevBridge must decide whether crash/recovery semantics are acceptable for its security/recoverability standard.

The native probe reports isolation tier (`base-container`, `appcontainer-bfs`, or `appcontainer-dacl`). DevBridge should likely surface/record the actual tier and consider whether some tiers should be refused by local policy or CI qualification.

### 4. Windows version floor

MXC currently documents Windows 11 24H2+ / build 26100+ for `processcontainer`, with different enforcement tiers/features by OS build.

DevBridge should verify the actual target Windows version/build explicitly and return one precise prerequisite message when unsupported.

### 5. Toolchain compatibility

The provider derives read-only tool roots from PATH and key Windows program/system roots plus explicit configured read roots.

This needs real CMake/MSVC/CTest/Node qualification. Do not broaden to the operator home just to make a tool work. Add narrowly justified toolchain roots if the boundary probe and real workload show they are needed.

### 6. Worker IPC staging

The Windows staging-result design must be verified against replacement, unlink, hard-link, reparse-point/junction, and parent-directory access attacks.

The authoritative anchored result file must remain unreachable/writable only by DevBridge control logic, never by the worker.

### 7. Process tree

The verification probe starts a detached descendant that attempts a delayed project write. The expected evidence is that the containment lifecycle kills the descendant when the sandboxed execution exits, so the marker never appears.

Also test timeout/cancellation through the normal ProcessRunner/DeterministicProcessRunner path, not only the provider self-probe.
