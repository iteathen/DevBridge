## Security contract that must not be weakened

Issue #49 and DB-003 require a Windows boundary equivalent in intent to Linux/Bubblewrap. At minimum, a supported Windows execution provider must demonstrate all of the following on the actual host:

- project/proposal and controller-owned run scratch are writable where intended;
- arbitrary outside-project reads are denied unless a root is explicitly authorized locally;
- writes outside DevBridge-owned execution roots are denied;
- DevBridge config/state/runtime authority and operator-home secrets are not readable by repository code;
- authoritative Git administrative state (`.git`, linked-worktree administrative paths) is not writable by the worker and preferably is unreachable;
- GitHub/SSH/Git askpass/control-plane credential channels are stripped from the worker;
- ordinary repository-code execution has blocked network egress by default;
- the whole relevant process tree is owned and terminated on normal exit, timeout, cancellation, or cleanup failure;
- local Windows toolchains needed by real workloads can still execute without broad host authority;
- `doctor` reports `available: true`, `verified: true`, and `repositoryCodeExecution: true` **only after** DevBridge's live adversarial boundary probe passes;
- a real Windows workload can run through the same boundary, including deterministic build/test and a coding/proposal worker;
- an end-to-end Windows canary reaches candidate sealing under control-plane authority;
- unsupported/unverified cases remain honestly fail-closed.

A provider binary's presence, a version string, or its own `--probe` output is never sufficient security evidence.

## Stable design pieces that survived every pivot

### 1. Control plane remains authoritative

Remote content can request work but does not grant machine authority. Git, state mutation, publication, leases, hard-gate decisions, daemon control, and authoritative result consumption remain outside the untrusted worker.

### 2. Windows worker IPC uses staging, not an authoritative writable mailbox

The Windows worker receives:

- an exact control-owned context file as read-only input;
- one non-authoritative pre-created staging result file as its writable output;
- no authority over the authoritative result object.

After contained execution is reconciled, DevBridge validates the staging object's identity/size and imports bytes under control-plane authority.

This design was introduced because Windows writable ACLs can include delete/replacement authority. Do not casually simplify it back to “worker writes the authoritative result file.”

### 3. Git-bearing projects use a Gitless proposal projection

This is one of the strongest useful outcomes of the investigation.

Instead of granting broad project write and then trying to subtract `.git`, a Git-bearing worker project is copied into a disposable proposal view that omits protected control/admin names. The worker edits the proposal view. DevBridge later imports ordinary project changes into the real worktree under controller authority.

Important hardening already added:

- `.git` and `.devbridge` are omitted/protected;
- protected-name comparison is case-insensitive, covering `.GIT` on Windows;
- the workspace uses a canonical real-path trust anchor so GitHub Actions host aliases such as DOS 8.3 `RUNNER~1` spelling do not cause a false rejection;
- new filesystem indirection beneath the trust anchor is rejected;
- source drift while the proposal runs causes import to fail closed;
- proposal import refuses alternate existing Windows names / real-path aliases before mutating the authoritative project;
- proposal import checks that the resulting authoritative project exactly reproduces the proposed non-Git state;
- `.git` sentinel state is checked to remain unchanged.

This projection is a valuable simplification even if the final low-level AppContainer engine changes.

## Investigation timeline and evidence

### A. Initial MXC 0.7 direct ProcessContainer approach

The original PR used the pinned Microsoft `@microsoft/mxc-sdk@0.7.0` runtime and built a ProcessContainer policy around:

- project/scratch writable paths;
- read-only executable/toolchain roots;
- denied control/Git paths;
- AppContainer/least-privilege settings;
- network denial;
- UI restrictions;
- live DevBridge canaries before claiming verification.

This was a reasonable starting architecture and **must not be described as disproven in principle**.

What live ARM64 evidence showed for our implementation:

- Windows 11 ARM64 host selected MXC `appcontainer-dacl`.
- Several important boundaries worked.
- Two security failures persisted on repeated fresh canaries:
  1. Git administrative state remained writable (`gitWrite:true`).
  2. A detached descendant survived long enough to write its escape marker.

That evidence proves only that **our MXC 0.7 configuration/integration did not satisfy DevBridge's boundary**. It does not prove that MXC, DACL denial, or ProcessContainer cannot be made safe.

Possible implementation-level causes considered included DACL grant/deny ordering/lifetime, nested writable-root semantics, and process-job ownership.

### B. Cross-platform Windows-path regression

A helper evaluating Windows executable paths used host path semantics on non-Windows CI. This produced a cheap cross-platform regression unrelated to the core sandbox security design.

The fix was to use Windows path parsing when evaluating Windows paths. Afterward, ordinary Ubuntu/Windows lanes returned green on the relevant checkpoint while ARM qualification continued to expose only the real Windows security failures.

Lesson: keep platform path semantics explicit and do not let cheap portability failures obscure live boundary evidence.

### C. Research into working Job Object/AppContainer patterns

External examples were studied to avoid inventing lifecycle mechanics from scratch.

Useful patterns found:

- Chromium and current MXC put kill-on-close semantics on the job that actually owns the sandboxed child/tree.
- Current MXC `main` has stronger Job Object lifecycle logic than released 0.7.0:
  - `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
  - job termination
  - accounting-based wait until `ActiveProcesses == 0`
  - bounded polling / fail-closed cleanup
- Current MXC AppContainer code uses `SECURITY_CAPABILITIES` through an extended process startup attribute list and uses an explicit handle list in pipe mode.
- Microsoft's `LaunchAppContainer` sample demonstrates the basic native pattern:
  - create/derive an AppContainer profile/SID;
  - build `SECURITY_CAPABILITIES`;
  - attach `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`;
  - create the child with extended startup info;
  - optionally use LPAC and mitigation policy.
- Microsoft AppContainer resource access is identity/resource-grant based; the sandbox identity must be granted access to exactly the resources it is supposed to use.
- At research time, the latest published MXC release was still **0.7.0**. Several hardenings studied in current MXC `main` were not available as a released version to simply pin.

These examples inspired later work, but none is a reason to assume our exact adaptation was correct.

### D. Outer DevBridge kill-on-close Job Object around MXC

An outer compiled helper was added so DevBridge could preassign the MXC launcher to a kill-on-close job.

The rationale was sound: do not rely on killing only an immediate launcher process.

Research then exposed a complication: MXC 0.7 creates/uses its own UI Job Object for the AppContainer child. Nested job behavior and UI-limit constraints made “outer job owns everything” less straightforward than expected.

More importantly, the live ARM64 compatibility canary on CI #674 showed a new concrete failure:

- the wrapped process exited `0`;
- the compatibility boundary got **no stdout and no stderr**;
- therefore DevBridge received no JSON observation payload and correctly refused to verify the provider.

That is evidence that **our wrapper's stdio/handle transport was wrong or incompatible in that composition**. It is not evidence that an outer Job Object can never work.

Do not restore this wrapper blindly, but do not discard the underlying lifecycle idea if a future implementation can own the actual sandboxed child and preserve stdio correctly.

### E. AppContainer SID reaper

A control-owned cleanup helper was implemented around a useful independent idea:

- derive the unique AppContainer SID from the per-execution container identity;
- enumerate running processes;
- inspect `TokenAppContainerSid`;
- match only the exact expected SID;
- terminate exact matches;
- require repeated empty sweeps before accepting cleanup;
- if a process is queryable and matches the SID but cannot be terminated, count it as a survivor and fail closed rather than pretending it was absent.

This was intended to work even when timeout/cancellation kills the outer launcher and when nested Job Objects make ancestor ownership unreliable.

This technique remains potentially useful as defense in depth even if the final engine uses a correct owning Job Object. Do not assume it is redundant until the final lifecycle has been proven under timeout/cancellation.

### F. Gitless projection instead of subtractive `.git` denial

The repeated `.git` DACL problem motivated a larger simplification:

**do not expose Git administrative state to the worker at all.**

A Gitless projection avoids depending on “grant project write, then subtract `.git` with denied paths” for the most sensitive repository authority.

This is currently the preferred project-view design because:

- it makes Git admin absence structural rather than a nested ACL exception;
- it aligns with the existing worker contract that Git metadata may be unavailable;
- it lets DevBridge import ordinary file changes only after process-tree cleanup;
- it keeps Git staging/commit under control-plane authority.

Again, this does not prove a correct ACL-only design is impossible. It reduces the number of things the OS sandbox must get exactly right.

## Windows path / filesystem lessons that must be retained

Windows path identity repeatedly caused false assumptions.

Keep these rules:

- lexical path equality is not filesystem identity;
- GitHub Actions may expose stable ancestor aliases such as 8.3 paths (`RUNNER~1`) while `realpath` returns the long spelling;
- accept host-managed aliasing **above** the trusted workspace anchor;
- reject new symlink/junction/reparse indirection introduced **below** the trusted workspace anchor;
- protected names must be compared case-insensitively;
- existing destination prefixes must be checked for alternate Windows names / canonical identity before proposal import;
- do not trust a string-level `.git` exclusion by itself on NTFS.

The Gitless projection tests already encode several of these cases. Preserve them even if the low-level sandbox changes.

## Risks / questions on the current native helper

These are review targets, not assertions that bugs exist.

### AppContainer creation and identity

- Is profile creation/derivation/deletion restart-safe and collision-safe for unique per-run IDs?
- Does cleanup fail closed if profile deletion fails?
- Are all SID allocations/frees correct on every error path?
- Is the process guaranteed to run under the exact AppContainer SID that received filesystem grants?

### ACL grant and restoration

The native approach necessarily grants the AppContainer identity access to selected host resources.

Review:

- exact access masks for read-only versus read-write paths;
- inheritance flags on files vs directories;
- whether existing ACLs are restored exactly, not approximately;
- what happens if the controller crashes between grant and restore;
- whether another concurrent verification/execution could mutate the same ACL;
- whether the current serialized task model is sufficient, including `doctor`/verification concurrency;
- junction/reparse/short-name/case behavior before every ACL mutation;
- whether granting a parent unintentionally exposes sensitive descendants;
- whether toolchain roots are broader than necessary.

A durable ACL cleanup journal may be warranted if exact restoration cannot be guaranteed across controller crashes.

### Process and handle ownership

Review:

- child created suspended;
- security capabilities attached before execution;
- intended stdio handles are the only inherited handles;
- actual sandbox child is assigned to the owning Job Object before resume;
- job uses kill-on-close;
- timeout/cancellation can terminate the job even if the launcher/helper is interrupted;
- accounting-based wait reaches zero before ACL rollback and proposal import;
- detached grandchildren cannot escape the job;
- SID reaping remains available as defense in depth if useful.

The ordering **process tree empty -> restore ACLs -> import proposal -> trust result** is security-sensitive.

### Network

The native provider currently supports deny-network mode only and rejects unrestricted mode.

Do not infer network denial from “no capability requested.” Keep the real blocked-egress canary as the authority.

If the helper uses no internet capability, verify actual behavior on the supported Windows host and retain the failure-closed rule.

### System/toolchain readability

A very restrictive AppContainer often cannot start ordinary Node/CMake/MSVC tooling unless required runtime/system paths are readable.

The current bootstrap/CI still performs MXC system-drive metadata preparation. That may be why.

If the native helper fails to start tools:

- do not immediately broaden arbitrary host reads;
- identify the specific system/toolchain resource requirement;
- grant the minimum resource needed;
- keep external reads deny-by-default;
- verify no control/credential root overlaps any added read root.

### UI restrictions

Current native helper uses standard Job Object UI restriction bits. Current MXC `main` contains build-aware handling for newer IME/input-injection flags.

Do not copy unsupported flags blindly. If stronger UI restrictions are needed, gate by actual OS support and preserve process startup compatibility.
