## 4. Why this next phase exists

Issues #4-#10 showed that asking a coding/model tool to perform deterministic machine operations causes avoidable ambiguity and overhead:

- shell quoting became the test rather than the intended boundary;
- model-side process/sandbox behavior was mistaken for PATCH-POLLER core behavior;
- trivial result-format fixtures consumed model turns/tokens;
- compiler discovery was incorrectly delegated to the worker environment;
- provider capacity could invalidate an unrelated durability test;
- Git staging/tracking semantics leaked into a worker that must not own Git state.

Issues #11-#17 showed the better direction:

- PATCH-POLLER-owned deterministic result parsing/recovery works;
- native compiler/linker/process probes are trustworthy;
- exact exit codes and streams can be captured without a model;
- persisted transient backoff/recovery works;
- a chat-authored multi-file C project can be built/tested/sealed without Codex/Spark;
- temporary tests can be created/run/reported with context and completely cleaned before sealing.

However, the later tests required another bespoke built-in profile/source module for each new scenario. That is now the primary design debt.

PP-013 generalizes the successful deterministic approach into a bounded controller-plan protocol.

## 5. Live evidence already proven

### Result protocol tolerance

- One UTF-8 BOM is accepted as presentation-only formatting.
- Ordinary JSON whitespace/line endings are accepted.
- Exactly one unambiguous plain/`json` Markdown fence around exactly one result object is accepted.
- Prose/multiple objects/multiple fences remain rejected.

Issue #11 proved the fenced-result live path after hardening.

### Structured result versus wrapper exit

A conservative valid structured `blocked`/`failed` result must not disappear merely because the wrapper later exits nonzero. Contradictory completion/nonzero cases are reconciled conservatively through normal validation/recovery.

### Windows filesystem identity/runtime stop race

Two Windows-specific failures were found and repaired during the campaign:

- canonical worktree identity now uses filesystem identity rather than fragile textual path spelling;
- daemon stop requests are atomically published so readers do not see a half-written stop request.

Both Windows and Ubuntu CI were green afterward.

### Native toolchain

PATCH-POLLER-owned local discovery found MSVC on the actual host and proved:

- valid compile;
- intentional compiler syntax error and diagnostic;
- repaired compile in same workspace;
- warning capture;
- valid link;
- native executable exact stdout marker;
- exact native exit code `17`;
- intentional unresolved-symbol link failure with `LNK2019`/`LNK1120`;
- repair/relink/re-execution;

This proved that the earlier model-side `exit 23 -> 1` observation was not a PATCH-POLLER ProcessRunner defect.

## 7. Security/authority rules that must not change

These are non-negotiable:

- PATCH-POLLER owns the Git index, staging, commit, task branch, push, and publication state.
- Chat/controller file contents are proposals until validated/sealed.
- Remote/controller data cannot grant capabilities.
- A controller plan is not a shell language.
- No remote executable path, shell fragment, arbitrary local path, environment value, credential, SDK path, cleanup root, or arbitrary Git ref becomes authority.
- Tool names resolve only through local registered adapters/configuration.
- Child processes use `shell:false` in generic deterministic operations.
- File writes/deletes remain canonical-path/no-follow contained.
- Secrets are not inherited by child operations unless a dedicated local adapter explicitly requires/scopes them.
- Output is bounded/redacted before GitHub projection.
- Human checkpoints remain checkpoint-and-proceed by default; do not turn this campaign into stop-and-wait development.

For **Phase A only**, the primary ChatGPT agent may use the same bounded chat-authored staging mechanism used during this campaign to place the initial controller-plan implementation on an isolated staging/testing branch. This is a bootstrap exception, not the target workflow.

Requirements for the bootstrap slice:

- no Codex/Spark/other coding model;
- ChatGPT authors the code directly;
- stage atomically from the exact current testing/foundation head;
- run cheap preflight first;
- require Windows + Ubuntu CI as applicable;
- use PATCH-POLLER live deterministic tests to exercise the new feature;
- do not add another task-specific built-in profile unless strictly needed to bootstrap the general controller-plan path;
- once controller plans are live, stop using bespoke profile/source embedding for ordinary feature implementation.

After Phase A, Phases B-D MUST preferentially use the new controller-plan/PATCH-POLLER mechanism itself, making the project increasingly self-hosting.
