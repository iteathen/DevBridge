## Implemented PP-017 behavior currently present on the branch

### 1. Immutable start baseline plus publication baseline

`src/git/workspace-manager.js` keeps:
- `baseSha` as immutable start-of-run evidence;
- `publicationBaseSha` as the baseline against which the candidate is currently verified for publication.

Changed-path calculation and `git diff --check` use `publicationBaseSha` rather than rewriting `baseSha` after upstream movement.

### 2. Fast-forward-only upstream reconciliation

Before final completion/publication PATCH-POLLER refreshes the managed repository and resolves the same persisted baseline ref.

- unchanged baseline: normal finalization continues;
- descendant/fast-forward movement: sealed candidate is rebased onto the new baseline;
- upstream history rewrite: fail closed into an explicit checkpoint path;
- rebase conflict: capture conflict paths, abort, verify exact pre-rebase head restoration, and do not leave an unresolved rebase behind.

### 3. Mandatory post-rebase reverification

`src/run/run-coordinator.js` invalidates pre-rebase verification evidence after successful baseline reconciliation.

- model-assisted runs must execute another bounded verification turn;
- deterministic controller plans replay the same validated plan/operations/assertions;
- prior test evidence is cleared from the current verification projection.

### 4. Publication recovery rechecks the baseline

A resumed run in `publishing` no longer blindly trusts a pre-crash seal. It re-enters final sealing/reconciliation and therefore detects upstream baseline movement that happened after the earlier verification.

### 5. Exact task-branch CAS and confirmed-remote predecessor rule

`src/git/workspace-manager.js` now:
- observes the exact remote task-branch head before mutation;
- uses an explicit empty expectation for first creation;
- remembers only exact remote heads that PATCH-POLLER itself confirmed through publication/reconciliation;
- allows a rebased rewrite only when the current remote head is one of those confirmed predecessor heads;
- refuses to overwrite an unexplained remote head even if the same commit exists locally;
- re-observes after push and accepts ambiguous transport only when the remote exact head converges to the intended commit.

### 6. Exact verified local candidate head binding

Current `src/git/workspace-manager.js` at `738d6bc...` contains the new publication interface:

`publishTaskBranch(workspace, { expectedHeadSha = null } = {})`

When `expectedHeadSha` is supplied it:
- validates the current clean local head equals that exact verified SHA;
- fails closed if the local head differs;
- pushes the exact SHA as `<localHead>:<ref>` rather than mutable `HEAD:<ref>`.

Current `src/run/run-coordinator.js` passes:

`{ expectedHeadSha: finalSnapshot.headSha }`

to `publishTaskBranch`.

### 7. Post-verification local candidate identity drift detection

Current `src/run/run-coordinator.js` also has `#recordLocalCandidateReverification(...)` and, on resumed `publishing`, compares the current candidate to the persisted verified snapshot.

It invalidates prior verification when:

- local HEAD differs from the verified head;
- the publication-baseline identity differs.

It clears current test evidence and sends the run back to `running` or `controller-plan` for reverification.
